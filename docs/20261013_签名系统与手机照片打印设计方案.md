## 1. 背景与目标

民政社会救助流程中，申请表、救助告知书、领取签收等文书需要**当事人本人签名**留痕。当前系统：
- 无任何签名采集、存储、嵌入能力（全仓库零命中，已核实）。
- 文书生成链路为「模板占位符替换 + Office COM」，纯文本替换，无图片插入能力。
- 手机端（Android）是主要数据录入终端，手机端不渲染文书，走**推送打印队列**（`nc_biz_print_jobs`）由 PC 端常驻打印代理消费。

**目标（第一批）**：在手机/桌面端采集手写签名 → 存库 → 文书渲染时自动内嵌到「本人签名」占位符位置。明确边界：签名是**生物特征留痕**，非 CA 认证电子签名，法律效力弱于手签+按印。

**已否决**：指纹采集系统（用户已确认去掉）。摄像头按压采指纹技术可行但成像质量不稳定、法律效力弱、《个保法》合规门槛高，本期不纳入。

## 2. 签名系统（已实施）

### 2.1 架构总览

```
┌─ 采集端（Android 触摸 / Windows 鼠标）─────────────────────┐
│  SignatureCaptureView (GraphicsView + IDrawable)          │
│        │ 笔迹（像素坐标 List<List<PointF>>）                │
│        ▼                                                  │
│  SignaturePngEncoder（纯托管栅格化 + PNG 编码）            │
│        │ PNG 字节（灰度图 800px 宽）                       │
└────────┼──────────────────────────────────────────────────┘
         ▼
┌─ 存储 ───────────────────────────────────────────────────┐
│  SignatureService → nc_biz_signatures（bytea 存 PNG）     │
│  按 applicant_id_card + business_type + signer_role 匹配  │
└────────┬─────────────────────────────────────────────────┘
         ▼
┌─ 嵌入（PC 渲染端）────────────────────────────────────────┐
│  PrintExecuteService.BuildSignatureImageMapAsync          │
│    → 取最新「本人」签名 PNG                                 │
│    → 按模板 config 的 SIGNATURE_* 占位符建图               │
│  ITemplateEngine.ReplaceImageFields                       │
│    → WordEngine: InlineShapes.AddPicture（COM）           │
│    → ExcelEngine: 空实现（默认接口方法）                    │
└──────────────────────────────────────────────────────────┘
```

**关键设计决策**

| 决策 | 选择 | 理由 |
|---|---|---|
| 签名存储 | **bytea 入库**（`nc_biz_signatures.signature_data`） | 仿 `nc_biz_templates.file_data` 先例；不落输出根 → 避开输出根迁移断链（§11 坑）；手机直写同一 PostgreSQL，无需跨端传文件 |
| 跨端传输 | **不走打印队列**，PC 渲染时按身份证号从库取回 | 队列 `fields_json` 是文本字典，塞 base64 污染且冗余；库取回对「手机采集→PC 打印」和「桌面直接打印」两条路径都生效，队列零改动 |
| PNG 编码 | **纯托管自研**（`ZLibStream` + CRC32） | 避免为「画粗线段+编码 PNG」引入 SkiaSharp 等原生包（Android so + Windows dll），收益不匹配风险 |
| 嵌入位置 | **Word COM `InlineShapes.AddPicture`** | 与现有管线最贴合；渲染本就在 PC 发生，正好匹配架构；docx 与 PDF 都带签名 |
| 文本/图片分流 | `SIGNATURE_*` FieldKey 前缀 | `MapFieldsToPlaceholders` 显式跳过签名 FieldKey，防止被 defaultValue 污染成文字；图片走 `ReplaceImageFields` |

### 2.3 数据模型

```yaml
# Resources/Schema/signatures/database.yaml
nc_biz_signatures:
  id              bigserial PK
  signature_data  bytea NOT NULL          # 签名 PNG（灰度，白底黑字）
  applicant_id_card varchar(30) NOT NULL  # 跨端匹配打印任务的关键字段
  business_type   varchar(50) NOT NULL    # 与打印 businessType 同口径（FamilyApplication 等）
  business_id     bigint NULL             # nc_biz_applications.id
  signer_name     varchar(100) NULL
  signer_role     varchar(20) NOT NULL    # 本人 / 代领人 / 经办人（默认 本人）
  created_by      integer NULL
  created_by_name varchar(100) NULL
  created_at      timestamp NOT NULL
indexes:
  idx_signatures_applicant_business (applicant_id_card, business_type, created_at)
  idx_signatures_business (business_type, business_id)
```

取回口径：`applicant_id_card + business_type + (business_id) + signer_role='本人'` 取 `created_at DESC LIMIT 1`。

### 2.4 模板接入方式（运营侧）

模板在 `nc_biz_templates` 运行时上传，无需改仓库文件。启用签名 = 在模板的 docx 中放签名占位符 + config_json 登记映射：

```jsonc
// config_json.fields 追加
{
  "placeholder": "{本人签名}",
  "fieldKey": "SIGNATURE_APPLICANT",
  "description": "申请人本人签名"
}
```

- 模板不放占位符 → 完全走原文本路径，零影响（纯增量，向后兼容）。
- 占位符可放在普通段落、表格单元格、文字框内——COM `Range.InlineShapes.AddPicture` 在三类位置都能落位（需按 §4 冒烟验证）。
- 签名框样式由模板设计控制，代码只负责「占位符位置插图 + 固定宽等比缩放」——改样式不发版。

## 3. 手机照片远程推送打印（设计方案）

> 未实施，待确认后立项。

### 3.1 需求

手机端拍摄/选择照片（如现场核查照、证件照、公示照片），推送到 PC 端默认打印机直接输出，无需先在 PC 上手工打开。

### 3.2 现有可复用资产

- **队列通道**：`nc_biz_print_jobs` + PC `PrintAgentService`（5 秒轮询、认领→执行→回写状态）已是成熟通道，本方案在其上扩展。
- **打印执行**：`PrintExecuteService` + `WordEngine`（Office COM）。

### 3.3 方案设计（已实施，批次二 + 批次三）

**照片采集存档（批次二）**：新建独立表 `nc_biz_archive_photos`（bytea 存库，仿 `nc_biz_signatures` 先例），按 `applicant_id_card`（跨申请按人聚合）+ `application_id` + `photo_category` 归档。类别四类：`ID_CARD` / `HOUSEHOLD_REGISTER` / `PUBLICITY_CHECK` / `OTHER_CERT`（`Constants/PhotoCategoryConstants.cs`）。采集/压缩（`Helpers/ImageCompressor.cs`，长边 ≤2000px、JPEG q85）/列表查阅在 `MobileArchivePhotoPage`。

**数据模型扩展**（`Resources/Schema/printing/database.yaml` 追加列；部署先行脚本 `docs/migrations/20261014_print_jobs_photo.sql`，SchemaService 启动幂等补列）：

```yaml
- name: job_kind        varchar(20)  NOT NULL default 'Template'   # Template=模板文书 / Photo=照片
- name: photo_data      bytea        NULL                          # 照片 JPEG 字节（单任务单张，PC 直接打印）
- name: photo_layout    varchar(20)  NULL                          # FULL_PAGE整页 / HALF_PAGE半页 / ID_CARD证件原寸
- name: photo_category  varchar(30)  NULL                          # 照片类别（展示/留痕用）
```

**入队（手机端）**：`MobileArchivePhotoViewModel.PrintPhotoCommand` —— 权限门控（复用 `PRINT_FAMILYAPPLICATION`，不新增权限种子）→ ActionSheet 选版式（证件类默认原寸，其余默认整页）→ `IPhotoPrintService` 无关，直接把压缩后的照片字节经 `PrintJobRequest{JobKind=Photo, PhotoData, PhotoLayout, PhotoCategory}` 交给 `IPrintQueueService.EnqueueAsync` 入队（Pending）。

**执行（PC 代理）**：`PrintAgentService.ExecuteJobAsync` 按 `JobKind` 分流：
- `Template` → 现有 `ExecutePrintAsync`（模板文书路径，不变）。
- `Photo` → 新增 `ExecutePhotoJobAsync` → `PhotoPrintService.PrintPhotoAsync`：Word COM `Documents.Add()` 空白文档 → `InlineShapes.AddPicture` 插入 JPEG → 按版式包围盒等比缩放（`PhotoLayoutConstants.GetBox`）→ 存临时 docx → 复用 `OfficeComDocuments.PrintFileAsync` 打印。全程走 `OfficeComWorker`（STA 串行 + 超时保护），与 `WordEngine` 同源。

**排版与压缩**：采集时即压缩（长边 ≤2000px、JPEG q85，单张约 200–500KB）；照片以 bytea **内联**入队（PC 直接打印，不回查照片表，避免跨表耦合）；单任务单张，多张=多次入队，避免单行过大拖慢轮询。

### 3.4 与签名系统的关系

照片打印独立于签名系统，但共享同一条 `nc_biz_print_jobs` 队列与 `PrintAgentService` 消费循环。两者不冲突：签名内嵌发生在 `ExecutePrintAsync` 内部，照片打印是并列的 `job_kind` 分支。

## 4. 验收与冒烟路径

> 本项目无测试项目，验证 = 编译零错误 + 启动冒烟（§0）。

### 4.1 编译

```bash
dotnet build NewCosmos.csproj -f net10.0-windows10.0.19041.0
# 需关闭正在运行的 NewCosmos.exe（否则 MSB3027 复制锁定）
```

已通过（0 个 C# 错误；唯一失败为运行中 exe 复制锁定）。

### 4.2 冒烟（签名链路）

1. **建表**：启动后 SchemaService 自动建 `nc_biz_signatures`（或查库确认表存在）。
2. **采集**：手机/桌面走「低收入申请」→ 填 Step1–5 → 保存 → 弹「采集签名」确认 → 去签名 → 手写 → 确认 → 提示保存成功。
3. **存库**：`SELECT id, applicant_id_card, business_type, signer_role, oct_length(signature_data) FROM nc_biz_signatures ORDER BY id DESC LIMIT 1;` 应有一行，`oct_length` > 0。
4. **嵌入**：在模板管理中给某救助模板 config_json 加 `{本人签名}` + `SIGNATURE_APPLICANT` 映射，并在 docx 对应位置放 `{本人签名}` 占位符 → 触发打印/生成 → 打开输出 docx/PDF，签名应出现在占位符处。
5. **回归**：不含签名占位符的模板打印结果应与改动前完全一致（验证零影响）。
6. **三位置验证**：同一模板在普通段落 / 表格单元格 / 文字框各放一处占位符，确认三处都正确插图（COM 落位，编译期无法验证，必须实测）。

### 4.3 失败容忍验证

- 采集时点「暂不」→ 保存/导航正常继续。
- 删除 `nc_biz_signatures` 中签名后打印 → 文书无签名、不报错、正常输出。
- 模板放了占位符但无签名 → 占位符保留（或走未解析占位符告警），不产生空图。

## 5. 风险、合规与后续演进

### 5.1 已知风险与缓解

| 风险 | 缓解 |
|---|---|
| COM 插图在文字框/表格内落位偏移 | §4.2 第 6 项三位置冒烟；必要时对 `InlineShape` 增加相对定位 |
| 签名 PNG 损坏导致 AddPicture 抛 COM 异常 | `ReplaceImageFieldOnWorker` 全 try/catch，仅 Warn，不阻断打印（§7 Result 之外的 UI 层容错） |
| 临时 PNG 文件残留 | `finally` 删除；`TemplateEngineHelpers` 临时目录启动清理兜底 |
| 同一申请人多次申请签名覆盖 | 取 `created_at DESC` 最新一条；如需历史可查全表 |

### 5.2 合规（重要）

- 签名属**生物特征个人信息**，《个保法》最敏感级别：需**单独同意**、加密存储、不得出内网。当前实现存库（内网 PostgreSQL），未做静态加密——**建议后续对 `signature_data` 启用 TDE 或列级加密**。
- **法律效力**：本签名是电子留痕，非 CA 认证签名，效力弱于手写签名+红印按手印。文书对外出具时应标注「电子签名留痕」。业务口需认可此口径。
- 审计：采集动作经 `_logger.LogBusiness("采集申请人签名")` 留痕（含 ApplicationId + SignatureId）。

### 5.3 后续演进方向（不在本批）

1. **签收签名**：当前系统无签收功能（代领人仅文本字段）。需配套新建签收记录表 + 移动签收页，工作量最大，建议单独立项。
2. **经办人/代理人签名**：`SIGNATURE_OPERATOR/AGENT` FieldKey 已预留，接入各自数据源（经办人可从登录态取）。
3. ~~**照片远程打印**：见 §3，待确认立项。~~ **已实施（批次二采集存档 + 批次三远程打印），见 §3.3。**
4. **签名重采入口**：档案/文书详情页提供「重新采集签名」按钮。
5. **列级加密 + 访问审计**：`signature_data` 加密存储，取回记安全日志（`LogSecurity`）。
