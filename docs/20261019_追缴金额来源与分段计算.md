# 追缴金额来源与分段自动计算（后补追缴）

> 更新日期：2026-10-19。**代码是唯一权威**：本文只解释口径与数据缺口，不改写实现。
> 权威实现：
> - 分段计算（唯一实现）：`Services\Domain\Recovery\RecoveryAmountCalculator.cs`
> - 历史取数（时间轴）：`Services\Domain\Recovery\RecoveryHistoryProvider.cs`
> - 常量与文案：`Constants\RecoveryConstants.cs`
> - 落库（含分段）：`Services\Domain\Recovery\RecoveryService.cs`
> - 界面：`Pages\Recovery\RecoveryFormPage.xaml`、`RecoveryManualPage.xaml`、`Pages\Mobile\MobileRecoveryFormPage.xaml`、`MobileRecoveryManualPage.xaml`
> - 建表/加列：`docs\migrations\20261019_recovery_amount_source.sql`

## 1 为什么改

原口径为「应追缴金额 = 月保障额 × 追缴月数」的单向派生，且界面只读：

- 来源档案月保障额为 0（台账行已不存在、历史变更不全）时，总额被算成 `0.00`；
- 编辑既有草稿再保存，会把库中已核定金额**静默清零**（真实数据丢失风险，同 §7「禁止吞异常返回空集」的道理）；
- 历史数据不完整的户（如张彦亮）根本没有可依据的月标准，业务需要的是**人工核实填写**而不是自动算出一个错数。

## 2 现口径（三分支）

`nc_biz_recovery_records.recovery_amount` 是**唯一事实来源**——表单、列表、打印、落库四处同源（`RECOVERY_AMOUNT` 取库值/表单值，不再各自反算）。自动计算只是生成该值的一种方式。

| 金额来源 `amount_source` | 含义 | 生成方式 |
|---|---|---|
| `Segment` | 自动分段累计 | 依据历史时间轴逐月取标准，标准变化即切段，Σ(段月标准 × 段月数) |
| `Flat` | 月标准 × 月数 | 无变更记录依据时按单一月标准定额（等价旧口径） |
| `Manual` | 人工核实填写 | 自动算不出，或自动值与业务事实不符 |

- `auto_amount` 保存「自动计算的参考值」：人工覆盖后仍保留，便于审计对比人工值与自动值的差异（界面提示「自动计算参考值」）。
- `amount_note` 为**人工填写原因**；`amount_source = Manual` 时保存前必填（表单校验拦截）。
- 自动可用时**仍允许手改**：用户改动总额且与自动值不一致即自动切换为 `Manual`（并要求填原因）；改回自动值则还原为自动来源标记。
- 编辑既有单据：**加载时原样回显库中已核定总额**，自动结果只作参考；只有用户改动「月保障额 / 追缴周期」才按新口径重算，且重算算不出时保留已核定金额（不清零）。

## 3 何时转人工填写（自动算不出的四种情形）

1. 起止月非法 / 追缴月数为 0；
2. 追缴跨度 > `RecoveryConstants.MaxAutoMonths`（默认 36 个月）——「追缴时间过长不自动算」；
3. 历史数据不全：某月之前取不到任何月保障标准（最典型：来源档案现值为 0、变更记录只有停发当月），提示会点名「YYYY-MM 之前无历史月保障标准」；
4. 按历史标准算得 0（无有效保障金月份）。

界面以黄色提示条给出原因，并自动切到「手工填写」并要求填写原因。

## 4 历史时间轴取数优先级（RecoveryHistoryProvider）

1. **现值（Ledger）**：低保/城市低保取 `nc_biz_applications.household_monthly_guarantee_amount`，为 0 时退化到台账 `nc_biz_*_families.monthly_guarantee_amount`（生效月 = 台账 `first_receive_month`，否则申请 `created_at` 月）；刚性支出取 `rigid_expenditure`；临时救助取 `confirm_amount`；高龄取 `issue_amount`。现值为 0 视为「无现值」，不作为锚点。
2. **保障金变更记录（ChangeRecord）**：仅低保系来源（`sourceId` 即 `nc_biz_applications.id`），取 `nc_biz_change_records` 中 `change_type ∈ {FundChange, CategoryStop}` 且 `new_guarantee_amount` 非空者，生效月 = 变更日期所在月。**分类施保**（`ClassifiedSubsidyReduce/Add`）金额不并入保障金口径，故排除。
3. **渐退期原标准（GracePeriod）**：**仅当现值缺失**时补 `nc_biz_grace_periods.original_guarantee_amount`（生效月 = 渐退期起月）。

明确**不做**的事：不用变更记录的 `old_guarantee_amount` 反推「更早的标准」（旧标准的生效起点无据可查，反推等于编造金额）。

时间轴为空/不足时取数器**返回空或不足的时间轴**，绝不构造金额。

## 5 分段明细表

`nc_biz_recovery_segments`（迁移脚本创建，列结构镜像 `nc_biz_elderly_payback_segments`）：`recovery_id / segment_no / monthly_amount / segment_start_month / segment_end_month / months / segment_amount / source`，外键 `ON DELETE CASCADE`（删记录即清分段）。界面「自动计算依据（分段明细）」可折叠查看，展示每段的起止月、月标准、月数与段金额。

> 该表未纳入 `Resources\Schema`（本库无 `recovery` 域，`nc_biz_recovery_records` 亦为手写建表），故结构变更一律走 `docs\migrations\*.sql`，不依赖 SchemaService。

## 6 已知数据缺口（决定"是否有自动值"）

| 缺口 | 影响 | 完善建议 |
|---|---|---|
| 无低保逐月发放台账（只有当前值） | 无法重建「历史逐月保障金」 | 建发放/核定台账（申请 + 生效月 + 月标准），或按月快照 |
| `nc_config_income_standards` / `nc_config_subsidy_standards` 无历史版本（各仅 1 行） | 无法按年份重建标准，也就无法推算历史月保障额 | 给标准表加生效区间（`effective_from/to`）或版本表 |
| `nc_biz_change_records` 仅覆盖 2026-02 起、来源多为停发当月 | 大多数户的时间轴为空 → 只能人工填写 | 历史变更补录/一次性导入，或从台账反推补录 |
| 台账行随停发被删（如张彦亮 `source_id=2521` 已不存在） | 现值取不到 | 停发归档保留台账行（软删），勿物理删除 |

结论：**在缺口补齐之前，「自动分段」只在历史完整的户上生效，其余户按设计转人工填写并留原因**——这正是本次改造要保证的行为（宁可让业务填，也不自动编造金额）。
