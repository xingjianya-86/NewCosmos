> 日期：2026-10-13 ｜ 触发问题：《档案_变更告知书》对梁玉祥户写出与自身数字矛盾的事实性错误。
> 范围：告知书理由生成、审计操作人留痕、最低工资标准配置。**不含** `nc_config_standards`
> 同类型多条 active 行的隐患（另开一轮，见 §7）。

## §1 问题现象与根因

### 1.1 现象

梁玉祥户（app94）的《档案_变更告知书》写道：

> 您家庭人均月收入 **713.92** 元 已超过低收入标准上限 **948.00** 元

713.92 **<** 948，"已超过"与自己的数字自相矛盾。

### 1.2 根因（两层）

**第一层 · 文案写死**（`ArchiveProductionViewModel.DocumentFields.cs:1299`）

```csharp
sb.Append($"您家庭人均月收入{perCapitaIncome:N2}元已超过低收入标准上限{threshold:N2}元，");
```

无条件写死"已超过"，不做数值比较。

**第二层 · 分流缺失**（`ArchiveProductionViewModel.cs:1017`，更严重）

调用点对**所有**停保记录无差别套用「收入超标」模板：

```csharp
_fieldData[FieldKeys.NOTICE_DETAILED_REASON] =
    await BuildIncomeExceededReasonAsync(app, newClassification);   // newClassification 被忽略
```

梁玉祥的 `newClassification` 是 **`IneligibleWithLabor`（有劳动力）**，根本不是收入超标。
库内 `classification_result = IneligibleWithLabor`，审计日志 `由 低保转入不符合认定条件（有劳动力）`。

真实判定逻辑在 `ClassificationService.cs:477`：

```csharp
if (!hasSevereCondition && hasLaborAbility)   // 无重病重残 + 有劳动力 → 不符合
```

**结论**：该户收入本就落在 632~948 的低收入区间**内**，被拒是因为家庭有青壮劳力，
与收入水平无关。文案把拒保理由归错了位。

## §2 法律边界：最低工资标准能写什么、不能写什么

实施前核对了三部文件，此边界直接决定文案措辞：

| 条款 | 最低工资标准的用途 |
|---|---|
| 《牡丹江市低收入人口认定实施细则》第十六条 | 就业必要成本 = **务工地两个月最低工资标准**，从收入中**扣减** |
| 同上 第四十五条 | 特困照料护理标准 = 当地最低工资标准的 1/4、1/6、1/10 |
| **其余条款** | **无** |

**「给有劳动能力未就业者按最低工资核定收入」在这套法规中不存在。**
上位法《社会救助暂行办法》第四十五条与《黑龙江省低收入人口认定办法（暂行）》第五十八条
走的是另一条路径：**就业推荐 + 连续 3 次无正当理由拒绝 → 才减发/停发**。

**因此**：最低工资标准**可写入文书，但只能作事实参照**
（说明劳动能力对应的收入能力 + 就业引导），
**严禁**写成"按 1910 元核算您家收入应为 X 元"——那是无法定依据的收入核定，
群众一申诉即被推翻，并连带动摇拒保决定本身的合法性。

该约束已写入 `WageStandardConstants` 类注释与 `BuildLaborIneligibleReasonAsync`
方法注释（要点 ②），防止后人"顺手"扩展成收入核定。

## §3 改动清单

### 改动 1 · 告知书理由按分类分流

| 文件 | 改动 |
|---|---|
| `ViewModels/ArchiveManagement/ArchiveProductionViewModel.cs` (~1016) | 调用点按 `IsLaborIneligible(newClassification)` 分流 |
| `ViewModels/ArchiveManagement/ArchiveProductionViewModel.DocumentFields.cs` | 新增 `IsLaborIneligible()`、`BuildLaborIneligibleReasonAsync()`、`LevelOrdinal()`；修正 `BuildIncomeExceededReasonAsync()` |

**1a. 分流**

```csharp
_fieldData[FieldKeys.NOTICE_DETAILED_REASON] = IsLaborIneligible(newClassification)
    ? await BuildLaborIneligibleReasonAsync(app, CancellationToken)
    : await BuildIncomeExceededReasonAsync(app, newClassification);
```

| `newClassification` | 走哪个生成器 |
|---|---|
| `IneligibleWithLabor` | **新增** `BuildLaborIneligibleReasonAsync` |
| `RuralIncomeExceeded` / `UrbanIncomeExceeded` 等 | 现有 `BuildIncomeExceededReasonAsync`（已修） |

**1b. 新增 `BuildLaborIneligibleReasonAsync`** — 五点设计（详见源码 XML 注释）：

1. **按分类说，不提收入超标**：显式点明"收入并未超标"，把拒保理由归位到成员状况
2. **工资标准只作事实参照**：§2 的法律边界
3. **标准读配置，缺失显式失败**：低保标准沿用 H4 惯例（缺 632/832 抛 `CONFIG_NOT_FOUND`）；
   **工资标准属补充性，缺失时省略该段 + 记 `Warn`**，不让文书生成整体中断——两者有意区别对待
4. **救济告知不写入**：模板《社会救助调整（终止）告知书》已含
   "如有异议，可自收到本告知书之日起15日内向我乡镇（街道）提出复查申请或60日内向\_\_申请
   行政复议或行政诉讼"，再写会重复
5. **刚性支出 >0 才提**：0 支出非本类拒保理由

**1c. 修正 `BuildIncomeExceededReasonAsync`（治本）**

```csharp
// 改前：无条件写死
sb.Append($"您家庭人均月收入{perCapitaIncome:N2}元已超过低收入标准上限{threshold:N2}元，");

// 改后：按数值判断，作为第二道防线
if (perCapitaIncome >= threshold)
    sb.Append($"...已超过低收入标准上限...");
else
    sb.Append($"...未超过低收入标准上限...");
```

即使将来有分支漏配，文案也不会与自身数字打架。同理删除了刚性支出为 0 时的
"且无刚性支出，不满足刚性支出困难家庭条件"赘句。

### 改动 3 · 最低工资标准三档（方案 B）

**政策依据**：黑政规〔2025〕1号，**2025-12-01 起执行，有效期三年**。

| 档 | 月标准 | 适用范围 |
|---|---|---|
| 第一档 | **2270 元** | 哈尔滨市区（呼兰/阿城/双城除外）、大庆市区 |
| 第二档 | **2010 元** | 牡丹江**市区**及绥芬河市、齐齐哈尔/佳木斯/鸡西/双鸭山/七台河/鹤岗/绥化市区、哈尔滨呼兰/阿城/双城、大兴安岭及所辖县市区 |
| 第三档 | **1910 元** | 伊春市区、黑河市区、**全省其他各县（市）** |
| 小时档 | 21 / 18.8 / 18.2 元 | |

**林口县 = 牡丹江市下辖县（非市区、非绥芬河市）→ 第三档 1910 元/月。**

**新增** `Constants/WageStandardConstants.cs`：

- 只存「区县 → 档位」映射 + 政策文号 + 生效日，**数值不硬编码**（§5.6、§11）
- `ResolveLevelType(district)`：精确匹配 → 按键长降序包含匹配 → 兜底第三档
- `IsDistrictKnown(district)`：供调用方判断是否记 Warn
- **未收录区县 → 回退第三档 + 记 Warn**（方案 A，不阻断文书生成）

**数据迁移** `docs/migrations/20261012_minwage_three_levels.sql`：

| standard_type | 值 | is_active |
|---|---|---|
| `MinWageLevel1` | 2270 | TRUE |
| `MinWageLevel2` | 2010 | TRUE |
| `MinWageLevel3` | 1910 | TRUE |
| `MinWage`（旧） | 1850 | **FALSE（软停用，不删）** |

三档用独立 `standard_type`，**不复用** `hukou_type`（既有语义 Rural/Urban）
与 `support_mode`（低保/特困）——复用会污染语义。幂等（按 `standard_type + is_active` 去重）。

**顺带查出的既有配置错误**（旧 `MinWage=1850`）：

1. 数值为黑政规〔2024〕1号**第二档**，2025-12-01 起已作废
2. 即便按 2024 版，林口县属**第三档（1750）**，1850 是**牡丹江市区**的值——**填错了档**
3. `effective_start_date` 写 2025-01-01，与实际生效日 2024-05-01 不符
4. **全库无任何业务代码读它**（仅 `StandardConfigManagementViewModel.cs:138`
   把它列进配置界面），故过期一年多从未暴露——本轮改动 1b 是**首次真正接入**

## §7 下一轮最高优先级：标准配置多条 active 行

`nc_config_standards` 中同类型存在**多条 active 行**，`StandardConfigService.cs:247`
只按 `standard_type + is_active` 过滤，**取值不确定**：

| standard_type | active 行 |
|---|---|
| `RuralSubsistenceStandard` | **632 和 585** |
| `UrbanSubsistenceStandard` | **832 和 780** |
| `RuralDestituteStandard`（分散） | 900 和 822 |
| `UrbanDestituteStandard` | 1076 / 1100 / 1300 三条 |
| `RuralSingleRescue` / `UrbanSingleRescue` | 各两条 |

**影响**：本轮文案取到 632（上限 948），但换个时机可能取 585（上限 877.5）——
**告知书数字会跳变**。分类计算一次会调用 `GetStandardValueAsync` 5+ 次，
若期间多行取值不一致，同一户的判定与文书可能自相矛盾。

建议：清理为每 `standard_type` + `hukou_type` + `support_mode` 组合**仅一条 active**，
历史行置 `is_active=false` 并用 `effective_start_date/end_date` 表达版本演进
（表结构已具备这两个字段）。
