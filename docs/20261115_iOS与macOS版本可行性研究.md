# iOS / macOS 版本可行性研究

> 2026-11-15。结论先行：**可行，但必须分阶段**。建议 iOS 先对齐 Android 版"数据录入端"功能子集，
> macOS 走 Mac Catalyst 顺带获得；完整办公功能（Word/COM 文书直出、PC 打印代理）本就是 Windows 端职责，不进移动端。
> 本文是技术盘点与路线建议，未动任何代码。

## 1. 现状盘点（移植友好面）

| 维度 | 现状 | 对移植的影响 |
|---|---|---|
| 目标框架 | `net10.0-android36.0` + `net10.0-windows10.0.19041.0`（`NewCosmos.csproj`） | 加 `net10.0-ios*` / `net10.0-maccatalyst*` 即可（.NET 10 MAUI 仍正式支持 iOS/MacCatalyst） |
| 分层 | Pages → ViewModels → Services → IDatabaseService，业务代码平台无关 | **绝大部分业务逻辑零改动**（约 95% 代码在共享层） |
| 平台服务抽象 | `Services\Platform\` 等处 ~11 个接口：`IFilePickerService`、`IFolderPickerService`、`IAlbumExportService`、`IAppPackageInstaller`、`ISystemBarsService`、`IPrinterService`、`IOcrRecognizeClient`（HTTP 远程）… 每端各自实现 | 每个接口补一份 iOS/MacCatalyst 实现（工作量主体之一） |
| 条件编译量 | `#if WINDOWS` 42 处、`#if ANDROID` 25 处 | 规模可控，多数是平台小片段而非业务分叉 |
| PDF 预览 | `Controls\PdfPreviewView` 用 **MAUI WebView + PDF.js**（base64 注入已规避 file:// CORS） | 跨平台，iOS 基本可用（WKWebView，需实测本地资源加载） |
| 打印 | 照片/文书推送打印走 `nc_biz_print_jobs` 队列，由 **PC 打印代理**（Word COM）认领执行；手机端只入队 | **iOS 无需本地打印**，天然规避最大的 COM 依赖 |
| 数据库 | PostgreSQL（Npgsql 纯托管） | iOS 可直连；内网可达性由部署方式决定（见 §4） |
| 图像管线 | SkiaSharp（官方支持 iOS/macOS）编解码/压缩/水印 | 直接可用（水印、WebP、缩略图同一套代码） |

### NuGet 依赖兼容表

| 包 | iOS/macOS | 备注 |
|---|---|---|
| SkiaSharp 3.x | ✅ | NuGet 自带 iOS 原生库；csproj 中现有 `Condition=android/windows` 的显式引用需补 iOS 分支 |
| Npgsql 10 | ✅（⚠️ AOT/裁剪需 `TrimmerRootAssembly` 或关裁剪） | iOS 默认全 AOT，Npgsql 反射映射需注意 |
| EPPlus / NPOI / ExcelDataReader | ✅ 纯托管 | 导入导出可用 |
| PDFsharp 6 | ✅ 纯托管 | iOS 可做 PDF 生成（替代部分 Word 直出） |
| CommunityToolkit.Mvvm（源生成）/ Serilog / BCrypt / TinyPinyin / YamlDotNet | ✅ | 源生成器与 AOT 友好 |
| Microsoft.Maui.Controls 10.0.90 | ✅ | 现有 XAML 管线（SourceGen inflator、GlobalXmlns）跨平台 |
| WebView2（启动动画/序列登录宿主） | ❌ 仅 Windows | `Components\AnimationWebViewView` 已把 WebView2 全部圈在 `#if WINDOWS`（5 段）；iOS 需第三套 WKWebView 虚拟主机/JS 桥实现，或首期禁用启动动画走经典登录 |
| Office/WPS COM（打印、文书直出） | ❌ | Windows 独有职责，iOS 不做（见 §1 打印行） |

| `System.Management` / 注册表（字体检测、Office 探测） | ❌ | iOS 直接返回不支持（已有 `#if WINDOWS` 模式） |
| 嵌入式 Python（彩票 LSTM，`python-embed`） | ❌ | iOS 禁用彩票预测模块（数据查询类功能可用，`nc_lottery_*` 在服务端） |

## 2. 阻塞项清单（按影响排序）

| # | 阻塞项 | 影响 | 方案 |
|---|---|---|---|
| 1 | **构建工具链需 macOS** | 无法在本 Windows 机直接出 iOS 包 | 装 Mac（或云 Mac：MacStadium/Codemagic/自建 Mac mini）；Windows 侧 `Pair to Mac` 可调试，CI 需 Mac runner |
| 2 | **iOS 分发** | 民政内网+公民敏感数据，上架 App Store 有审核与数据合规风险；App 内自更新（`IAppPackageInstaller`）被 iOS 禁止 | 三选一：Ad Hoc 签名（每台设备录 UDID，≤100 台）/ TestFlight（90 天，需外审）/ 企业证书（$299/年，国内获取门槛高）。**建议 Ad Hoc + 内部 OTA 清单页（itms-services 协议）**，把 `IAppPackageInstaller` 的 iOS 实现做成"跳 Safari 安装 itms-services 清单" |
| 3 | **自定义相机** `Controls\CameraPreviewView` + Android `CameraPreviewViewHandler`（OCR 扫描页定向拍摄） | OCR 扫描页 iOS 缺实现 | 首期 OCR 扫描页用 `MediaPicker.CapturePhotoAsync` 兜底（识别回填链路不变，只损失实时取景框），二期再写 AVCapture Session handler |
| 4 | **启动动画/序列登录宿主** WebView2 虚拟主机 + JS 桥 | iOS 无 WebView2 | 首期 `LoginStyle=classic`（已有回退通道）或用 WKWebView 复刻 `AnimationWebViewView` 的非 Windows 路径（中等工作量，纯 UI 可后置） |
| 5 | **Android 专属包可见性/VPN**（ZeroTier 查询、APK 自更新） | iOS 无对应概念 | 按平台裁剪：内网可达性改 VPN/局域网配置说明，更新走 §2.2 |
| 6 | **csproj 条件项**（SkiaSharp 显式引用、WindowsAppSDK、Android 资源） | 新 TFM 编译报错 | 逐条补 `Condition="'$(TargetPlatformIdentifier)' == 'ios'"` 分支；`Platforms\iOS\`、`Platforms\MacCatalyst\` 目录补齐入口与服务实现 |
| 7 | **Npgsql + 全 AOT** | 裁剪警告/运行时映射风险 | iOS 首发关 `PublishTrimmed`（体积换稳定），压测查询映射 |

## 3. 分阶段路线建议

### Phase 0 — 决策与基建（1~2 周）
- 拿到 Mac 硬件 + Apple 开发者账号，确定分发方式（建议 Ad Hoc + 内部 OTA）
- `dotnet workload install ios maccatalyst`，csproj 加 TFM 与条件项，空工程跑通登录 + 数据库连接冒烟

### Phase 1 — 数据录入端子集（4~6 周）⚠️ 核心价值
目标 = **Android 版功能等价**（本项目的移动端定位就是数据录入端）：
- 平台服务 11 接口的 iOS/MacCatalyst 实现（文件选择/相册导出/系统栏/网络状态等，均是薄封装）
- 三大业务表单 + 列表 + 导入 + 档案照片采集（**拍照/水印/压缩/上传零改动**）+ 补传 + OCR 识别（服务端 HTTP）
- DPAPI → Keychain；打印推送照常入队（PC 端打印）
- 禁用：启动动画（走经典登录）、彩票预测、Word/COM 直出（导出走"推送到 PC"或 PDFsharp）

### Phase 2 — 体验补齐（2~4 周）
- WKWebView 版动画宿主（启动动画/序列登录）、OCR 实时取景 handler、PDF 预览 iOS 实测与修正
- Mac Catalyst 桌面适配（窗口/快捷键已有 `WindowTitleService` 等抽象可复用）

### Phase 3 — 办公输出边界（可选）
- 需要 iOS 本地出文书时用 PDFsharp 生成 PDF（模板体系是 Excel/Word，需另评估 Word→PDF 渲染路径）；或维持"iOS 录入 → PC 出文书"分工不变

**总量粗估**：Phase 0+1 ≈ 5~8 人周可上线内测；全功能对齐另计。最大不确定性不在代码（架构已隔离良好），而在 **Apple 分发/审核政策** 与 **Mac 设备获取**。

## 4. 关键决策点（需要业务侧拍板）

1. **分发方式**：Ad Hoc（设备数上限、换机需重签）vs 企业证书（门槛）vs TestFlight（外网+审核）——决定 `IAppPackageInstaller` iOS 实现形态
2. **iOS 版功能边界**：是否接受"数据录入端"子集（与 Android 版同口径）还是要求全功能
3. **数据库可达性**：iOS 设备如何进内网（VPN/同 WiFi/反向代理），`config\database.ini` 的凭据保护改 Keychain 方案是否可接受
4. **Mac 与开发者账号预算**

## 5. 结论

- **技术上可行**：架构分层 + 平台服务接口 + 条件编译隔离已经把平台耦合压到较低水平；核心链路（表单、照片采集、水印、OCR、打印队列）在 iOS 上基本是"原样复用 + 薄平台适配"。
- **商业/合规上需先决策分发方式**，这是 iOS 项目真正的第一道门。
- **建议先做 Phase 0 冒烟验证**（1 台 Mac + 1 台 iPhone 跑通登录→查询→拍照上传），再决定是否立项 Phase 1。
