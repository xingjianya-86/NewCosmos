## 1. 业务口径

模板全库唯一（`nc_biz_templates` 241），「停保 / 不予认定 / 终止 / 待遇调整」是同一模板的不同**方向**，
方向由 `ArchiveProductionViewModel` 装配端按事实分支填 `NOTICE_*`。方向②的判定规则：

| 方向 | 判定条件（原分类） | 典型场景 |
|---|---|---|
| **停止 / 停止享受** | 原分类为**有效分类**（非停保码）→ `wasInScope=true` | 曾在保，因收入超标等被停保 |
| **不予认定** | 原分类为**停保码**（收入超标/不予认定族）→ `wasInScope=false` | 首次申请即被拒（真·首拒） |

**原分类三级取值（2026-11-19 起）**：
1. 变更记录 `old_classification`（CategoryStop 等记录的"变更前分类"）；
2. **链上前分类**（`Helpers\ChainPreClassification`：链上最近一条非空 `old_classification` → 回退
   `original_application_id` 上游链最近非空分类）——新增级；
3. 档案自身 `classification_result`（末级回退）。

> 2026-11-19 收口前：归档终结拒保兜底**直接拿档案自身停保码当原分类**，链上有在保前分类也不看 → 一律「不予认定」。

## 2. 根因（丁玉花 app113 实据）

| 档案 | 事实 |
|---|---|
| 112（上游，2人） | 农村低保 `RuralLowIncome`；2026-11-18 户主死亡停保（变更记录64 `HouseholdDeath` 112→113，old=RuralLowIncome） |
| 113（丁玉花，1人） | 112 死亡停旧建新产物（source=HouseholdDeath, original_application_id=112）；分类判 `RuralIncomeExceeded`（收入超标）→ 08:51 完成归档 →「归档终结：判定不合格」置 Stopped（**只写 stop_reason/stop_date，不写变更记录**），链上无 CategoryStop |

装配端方向②取原分类：记录 old 为空 → 走归档终结拒保兜底 → **原分类=自身停保码** → `wasInScope=false`
→ 误出「不予认定」。业务事实是"曾享受（前分类=农村低保）→ 收入超标被拒"，应为「停止」。

**影响面（当时库内同形态 5 户核对）**：83/99/105 有 CategoryStop（old=低保/特困）走主分支方向本就正确；
110 无任何链证据（真·首拒）应保持「不予认定」；**仅 113 被误判**。

## 3. 修复（A + B）

### A：装配端判向（`ViewModels\ArchiveManagement\ArchiveProductionViewModel.cs`）

- 归档终结拒保兜底：先取链上前分类 → `NoticeStopDirection.ResolveArchiveRefusedOriginal(前分类, 自身停保码)`
  （在保前分类 → 原分类=前分类 → 「停止」；取不到/前分类本身是停保码 → 自身停保码 → 「不予认定」）。
- 方向②原分类三级回退补第 2 级（记录 old 为空的存量行同收口）。
- 取数失败降级为 null + `Warn`（沿用 stopRecord 降级模式，不阻断打印）。

### B：写入侧补记录（`Services\Core\ApplicationStatusService.cs`）

`CompleteArchiveAsync` 落 Stopped 的**同一事务内**补写 CategoryStop：

- 字段：`old=链上前分类`、`new=自身停保码`、`change_reason_type='归档终结拒保'`（新常量
  `ChangeReasonTypeConstants.ArchiveRefusalStop`，**不复用**现有值防"最近一条"取数误读）、
  `triggered_stop=TRUE`、`change_date=stop_date`、**金额两列 NULL**、`new_application_id=NULL`、
  `change_category=NULL`（不入增减员调整表）。
- 守卫：① 自身为停保码；② 链上前分类非空且非停保码（否则=真·首拒，跳过+LogInfo）；
  ③ 链上无既有 CategoryStop（幂等）。失败 → **回滚归档**（与经济复核 `WriteCategoryStopRecordAsync` 先例一致）。
- **直写 SQL、不注入 IChangeService**：`ChangeService → IApplicationService → IApplicationStatusService`
  构成 DI 构造环。链上前分类与装配端共用 `Helpers\ChainPreClassification`（单点，两侧不劈叉）。

### 清单门（`Services\Domain\ChangeManagement\ChangeDocumentApplicabilityService.cs`）

- `QueryLinkedChangeTypesAsync` 改取 `(change_type, change_reason_type)`；
  `hasEconomicReview` 抽纯函数 `CountsAsEconomicReview`：`CategoryStop + 归档终结拒保` **不计**复核类
  （该档从未经过复核行为，计入会让《档案_定期复核审批表》/「经济复核」叶子误开放）。
- `IsArchiveRefusedStop` / 方向表注释同步：本门只管"出不出模板"，方向由装配端按链上前分类决定。

### 存量补录（`docs/migrations/20261119_archive_refusal_categorystop.sql`）

形状：`Stopped + 自身停保码 + stop_reason LIKE '复核判定不合格%' + 链上无 CategoryStop + 链上有非停保码前分类`
→ 当前库**命中档案113**（83/99/105 已有记录、110 无链证据，均被排除）。已执行 + `-Mark` 登记。
