# 证件 OCR 识别（Xiaomi-OCR-0）与定向回填

> 2026-11-03。内网部署的类别驱动证件识别：照片 + 类别 → 服务端 KIE 抽取 → 分配页用户定向回填。

## 一、总体架构

```
手机拍照/Windows 选图（档案照片页 + 扫描页）
      ↓ 图片 + 类别
内网 OCR 服务（192.168.0.2 / ZeroTier 10.110.0.2:8788）
  ├ nc-ocr-api（FastAPI，deploy\ocr\ocr_api.py）
  └ nc-ocr-ollama（Xiaomi-OCR-0 BF16，num_ctx=8192，仅容器内网）
      ↓ {fields, lines}
识别结果分配页（OcrAssignPage）→ 用户选回填去向 → 表单回填（只填空字段）
```

- **模型**：Xiaomi-OCR-0（0.8B 文档理解 VLM，社区 BF16 GGUF `longwayxu/xiaomi-ocr-0:bf16` + 视觉投影器 ≈1.8GB）。
  推理管线（图像预处理/KIE 提示词/解码参数）逐项复刻官方 `mcp_ocr_server.py`，对齐说明见 `deploy\ocr\ocr_api.py` 文件头。
- **PII 边界**：图片仅走内网（LAN/ZeroTier 双网卡绑定），不出外网；日志只记类别/耗时/脱敏证号，不落图片与识别文本（§10）。
- **断网行为**：识别不可用（端侧 PP-OCR 已移除），显式失败提示；照片存档不受影响。

## 二、9 类识别映射（`Constants\OcrFieldKeys.cs` ↔ `deploy\ocr\ocr_api.py` CATEGORY_FIELDS）

| 类别 | 模式 | 抽取字段 | 回填策略 |
|---|---|---|---|
| ID_CARD | KIE | name, id_card, address | 姓名/证号 → 申请人（校验码核验，不符带警告徽标）；背面住址 → 家庭住址（级联） |
| HOUSEHOLD_REGISTER | KIE | head_name, hukou_address | 户籍地址/户主姓名（只填空） |
| BANK_CARD | KIE | bank_name, card_number | 开户行/银行卡号（只填空） |
| MEDICAL_RECORD | KIE | diagnosis, hospital, date | 申请事由详情/困难原因（只填空） |
| DISABILITY_CERT | KIE | cert_no, disability_type, disability_level | 成员行残疾证号 → 自动触发现有解析联动 |
| INCOME_PROOF | KIE | employer, amount, period | **仅展示**（§9 金额铁律：不自动落金额） |
| PUBLICITY_CHECK / OTHER_CERT | 文本 | — | 仅展示（弹窗文本供手抄） |
| PERSON_PHOTO | **不识别** | — | 纯照片，服务端拒绝 400 |

字段键是双端契约，**改一边必须同步另一边**。

## 三、交互流（设计定稿 2026-11-03）

1. **上传后询问**：保存成功 → 弹「读取识别（Xiaomi-OCR-0）· N 张 · 预计耗时（每张约 5–15 秒）· 图片仅走内网」→ [开始识别/跳过]。
2. **逐张识别**：LoadingOverlay 阻塞等待，进度「正在识别 2/3…」；单张失败不阻断其余。
3. **分配页定向回填**（`OcrAssignPage`）：每条记录一张卡片——字段可编辑 + 校验码警告徽标 + 原始文本；
   目标下拉 = 表单上下文提供（户主/各成员行/新增赡养人/表单字段）+「不使用」。
   - 预匹配：证号命中 → 该行；姓名命中 → 该行；**名单外人物记录默认「新增赡养人」**（快速核查页=新增子女授权人行）。
   - 冲突（同目标多条）→ 弹「覆盖/改选」；覆盖 = 保留最后一条。
   - **只填空字段**，防误覆盖。
4. **完成**：回传实际回填条数 → 来源页 SnackBar「已回填 N 条」。

两入口（均走完整流程）：**档案照片页**（批量多选逐张全识别，跨平台 Windows 也走这里）+ **扫描页**
（`MobileOcrScanPage`，Camera2 取景，类别选择器，取景框仅身份证类别显示）。

### 地址类回填铁律：先解析、后回填（2026-11-05）

地址（户口本户籍地址 / 身份证背面住址）**不得边匹配边写表单**：旧村名、自然屯（如「工农屯」）
在 `nc_regions_villages` 里查无此名，旧实现会在匹配到市/县后清空子级选项并提前返回，
再叠加 Picker 的 TwoWay 空值回写，表现为"扫描后户籍乡镇/村变空、保存草稿被拦截"。

现行规则：

1. **Resolve（只读）**：按 市→县→镇→村 逐级查库 + `MatchRegionOption` 匹配，四级全部命中才产出回填计划；
   任一级不匹配或任一查询失败 → 返回失败原因，**表单零改动**。
2. **Commit（一次写入）**：候选选项与选中值一次性同步写入（`_suppressRegionCascade` 期间），
   全程不再查库，不存在"选项已清空、新数据没回来"的中间态。
3. **村级歧义不猜**：`MatchVillageOption` 要求唯一命中；多个村共用词干（如「石青村委会」「石青村」）
   一律视为不匹配，交人工选择。旧村名/自然屯按后缀归一（村委会/村民委员会/居委会/社区/村/屯）能对上的仍会自动命中。
4. **未回填可见**：失败原因经 `IOcrAssignContext.Warnings` 汇总到分配页弹窗（"户籍地址未回填：未匹配到村/社区…"），
   不再静默保持原值。
5. **选项加载先查后换**：`LoadHukou*/LoadFamily*` 查询失败时保留旧选项与旧选中值，避免同类"被清空"问题复现。

## 五、服务端部署（deploy\ocr\）

- `docker-compose.yml`：`nc-ocr-ollama`（mem≤3G，KEEP_ALIVE=24h 保温，**不发布宿主端口**）+
  `nc-ocr-api`（mem≤300M，只绑 192.168.0.2/10.110.0.2:8788）。
- `setup_model.sh`：拉 BF16 包 + 派生 `nc-ocr:ctx8192`（Ollama 默认 num_ctx 不够整图 token 预算）。
  ⚠️ `docker exec` 必须 `-i` 才能接住 stdin 的 Modelfile（漏了报 "no FROM line"）。
- `pipeline_smoke.sh`：合成图冒烟（ID_CARD/BANK_CARD KIE + PERSON_PHOTO 拒绝）。
- 实测（i3-4170 CPU）：冷启动 22s，热调用 4.5–16s/张；内存 2.14G/3G。
- 基础镜像走 `docker.1ms.run`（docker.io 直连超时、daocloud 源 401）；pip 走阿里源。
