## 4. 客户端兼容性与升级要求

**结构层向后兼容（不需要「停服 → 迁库 → 启服」）：**

| 场景 | 旧客户端行为 | 结果 |
|---|---|---|
| 新增追缴记录 | INSERT 不带三列 | `amount_source` 取默认 `'Flat'`，不报错 |
| 查询列表 / 打印 | 只读 `recovery_amount` 等原列 | 不受影响 |
| 旧版 SQL 无 `SELECT *` 依赖 | 明确列名 | 不受影响 |

**业务层有一处已知风险：**

- 旧版 `RecoveryService` 保存时按 `recovery_amount = monthly_amount × recovery_months` 重算并落库，且不写 `amount_source`。
- 因此在旧版上编辑 id=3（张彦亮）→ 金额被改回 `0.00`，而 `amount_source` 仍是 `Manual`（原因字段还在），出现「手工核实但金额为 0」的矛盾态。
- **处置**：1.1.20261019 已发布且 `minSupportedVersion` 等于该版本，旧客户端会被要求升级；**在终端完成升级前，追缴单据一律走新版客户端编辑**。

新版客户端内部行为（供验收对照）：

- 打开既有单据：原样回显库中金额与来源，自动计算结果仅作参考，不覆盖；
- 只有改动「月保障额 / 追缴周期」才重算；重算算不出时保留原值不清零；
- 算不出时黄条提示并转手工填写，`amount_note` 必填。

## 6. 回滚方案

### 6.1 只回滚「金额来源」改造（推荐的最小回滚）

```sql
BEGIN;
-- 数据：用备份表还原 id=3 原值
UPDATE nc_biz_recovery_records r
SET monthly_amount  = b.monthly_amount,
    recovery_amount = b.recovery_amount,
    updated_at      = NOW()
FROM nc_biz_recovery_records_bak_20261019_source b
WHERE r.id = 3 AND b.id = r.id;

-- 结构：仅在确认新版客户端已全部停用时执行（会丢弃来源与分段信息）
DROP TABLE IF EXISTS nc_biz_recovery_segments;
ALTER TABLE nc_biz_recovery_records
    DROP COLUMN IF EXISTS auto_amount,
    DROP COLUMN IF EXISTS amount_note,
    DROP COLUMN IF EXISTS amount_source;
COMMIT;
```

注意事项：

- **不要回滚 `20261019_recovery_amount_fix.sql`**：它把 16301 落库，回滚即恢复为 0.00（错误业务值）。若必须回滚，只能用该脚本的备份表 `nc_biz_recovery_records_bak_20261019_amount` 人工逐行确认。
- 回滚前先 `pg_dump -t nc_biz_recovery_records -t nc_biz_recovery_segments` 留档；两张 `*_bak_20261019_*` 备份表建议保留至下一发版周期结束。
- 结构回滚后，新版客户端会因缺列报错，故只能在「客户端已回退 + 服务端确认无新版连接」时执行。

### 6.2 全量回退到迁移前

1. 回退客户端到上一版本；
2. 执行 §6.1 的结构回滚；
3. 用 `20261019_recovery_amount_fix.sql` 的备份表还原 id=3 金额（0.00），并按业务纸质凭证重新核定。

## 7. 新环境 / 灾备库执行步骤

按顺序执行，每步失败即停止（`psql -v ON_ERROR_STOP=1`）：

```powershell
# 0) 备份（必做）
pg_dump -h <host> -p 5432 -U <user> -d <db> -t nc_biz_recovery_records -f backup_recovery_$(Get-Date -Format yyyyMMdd_HHmmss).sql

# 1) 存量订正（仅当库中存在 id=3 张彦亮；不存在则 no-op）
psql -h <host> -p 5432 -U <user> -d <db> -v ON_ERROR_STOP=1 -f docs\migrations\20261019_recovery_amount_fix.sql

# 2) 结构 + 回填（幂等）
psql -h <host> -p 5432 -U <user> -d <db> -v ON_ERROR_STOP=1 -f docs\migrations\20261019_recovery_amount_source.sql

# 3) 核验（只读）
psql -h <host> -p 5432 -U <user> -d <db> -v ON_ERROR_STOP=1 -f docs\migrations\20261020_recovery_online_verify.sql
```

顺序说明：`fix` 必须在 `source` 之前——两者顺序颠倒虽也能得到 16301，但 `fix` 的备份表会记录 0.00，回滚依据变差。

幂等性：两个脚本均用 `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` / `IS DISTINCT FROM` 守卫，重复执行不产生副作用。

## 8. 遗留数据缺口（影响自动分段命中率）

| # | 缺口 | 影响 | 建议优先级 |
|---|---|---|---|
| 1 | 停发时台账行被物理删除，丢历史月标准 | 现值取不到 → 只能人工 | **高**：改为状态标记（如 `is_active=false`）不再物理删 |
| 2 | `nc_biz_change_records` 仅覆盖 2026-02 起 | 早期标准变化无法分段 | **高**：补录历史变更 + 后续强制留痕 |
| 3 | 标准表（`nc_config_income_standards` 等）无生效区间，只存单版本 | 无法回看历史标准 | 中：加 `effective_from/effective_to` |
| 4 | 无逐月发放台账（`nc_biz_elderly_paybacks` 类结构未覆盖追缴来源） | 自动计算只能靠「现值 + 变更记录」拼 | 中：按 §1 口径逐步补齐 |

在上述缺口补齐前，自动分段只在历史完整的户上生效，其余按设计转人工填写（`Manual` + 原因），这是预期行为，不是缺陷。
