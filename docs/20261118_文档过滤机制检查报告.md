# 文档过滤机制检查报告

> 日期：2026-11-18。触发：新增两张一事一议模板时，原 `Contains("一事一议申报表")` 门槛匹配不上新表名，
> 被迫放宽为子串匹配 + 排除补丁，暴露文件名过滤的系统性脆弱。
> 结论已决策：**方案 B（二维精准过滤：项目类型 × 文档类型）**，白名单一并改为按文档类型传参。

## 一、现状：两套机制并存

### ① 分类过滤（主体，已具备二维雏形）

- `nc_biz_templates.categories`（text[]，现库 37 个分类值）是唯一数据源
- 项目类型维度：`ArchiveCategoryResolver.GetRecordCategories(businessType, classification, operationOverride)`
  把 6 个业务域（FamilyApplication / TempRelief / ElderlyBenefits / AssetVerification / MonthlyReport / Recovery）
  + 保障分类码 + 业务操作（新增/停止/经济复核…）映射成分类集，`GetByCategoriesAsync` 用 `categories && $1` 交集取模板
- 适用性事实过滤：`ChangeDocumentApplicabilityService.IsTemplateApplicable(t.Categories, docFacts)`
  —— **按类型 + 按事实，是全库做得最对的一处**
- 补打中心：`GetReprintDomainCategories` 优先按分类，仅未接入域回退名称前缀

### ② 文件名过滤（散落约 33 处，问题所在）

## 三、为什么脆弱 —— 实例

新增两张一事一议表后，原门槛 `Contains("一事一议申报表")` 匹配不上新表名
（`档案_社会救助"一事一议"申请表`），被迫放宽成 `Contains("一事一议")` 再打
`!Contains("会议记录")` 补丁防误伤月报表。

**文件名过滤的典型代价**：每新增一张模板都要记得改代码门槛，否则模板静默不出现在清单；
改名则全部判定失效。

## 四、二维维度现状对照

| 维度 | 现状 |
|---|---|
| **项目类型** | ✅ 已有：`businessType` + `classification` → `ArchiveCategoryResolver` 映射分类集，链路完整 |
| **文档类型** | ⚠️ 半有：`categories` 里已有部分文档类型叶子（`证明文件`、`档案_变更告知书` 等），但与项目类型混在同一维多值标签；`file_type`（xlsx/docx）只用于选引擎；一事一议/近亲属/土地等无对应分类，只能靠名字 |

## 五、决策：方案 B

```
过滤 = 项目类型（businessType + classification → categories，已有，不动）
     × 文档类型（新增 nc_biz_templates.doc_type 单值列，取代一切 Name.Contains）
```

1. 新增 `doc_type` 列 + `TemplateDocTypes` 常量词表（单一来源）
2. 模板上传时必选文档类型；存量 75 张迁移回填
3. 代码定位模板一律 `GetByDocTypeAsync(docType)`，清除全部 Contains 模糊匹配
4. `TemplateFilter`/`PrefilterTemplateNames` 改名 `TemplateDocTypeFilter`/`PrefilterDocTypes`，
   语义从"模板名[]"改"文档类型[]"（编译器强制所有调用点显式适配，杜绝静默漏改）
5. 项目类型维度（categories / ArchiveCategoryResolver / IsTemplateApplicable）保持不动

## 六、预期收益

- 新增模板只需在上传时选对文档类型，**零代码**即可正确进入清单
- 模板改名不影响任何过滤逻辑
- 全库无 `Name.Contains` 模糊匹配残留
