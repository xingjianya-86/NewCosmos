# 死亡情况说明与死亡申报台账规范

> 更新：2026-10-26（首版）。适用：「死亡情况说明」功能全链路（申报 → 身份聚合 → 数据提醒 → 跨流程联动 → 文书输出）。
> 单一事实来源：可执行逻辑以源文件为准；本文只保留规则、口径与挂点索引。
> 相关迁移：`docs/migrations/20261026_death_declarations_and_death_time.sql`

## 1. 需求与已定决策

| # | 决策 | 结论 |
|---|---|---|
| 1 | 输出对象 | 单人一份文书 |
| 2 | 身份口径 | 死者本人在库身份，**七类源全含**（仅本村命中） |
| 3 | 提醒形式 | 界面列表 + 文书附段（同一份规则表） |
| 4 | 入口 | 独立页面（PC + 手机端）+ 首页第四条横幅 |
| 5 | 范围 / 权限 | **严格按本村**（未绑定村社区显式失败）；输出复用 `PRINT_LOWINCOMEPROOF`，申报写入复用 `CHANGE_MANAGE` 口径的业务页 |
| 6 | 跨村记录 | 不进身份表，只计数进提醒 |

| 8 | 申报台账 | 新表 `nc_biz_death_declarations`，**死亡确切时间必填**，允许多次申报 + 作废 |
| 9 | 旧流程 | 户主死亡变更 / 成员死亡一并改成填确切时间 |
| 10 | 跨流程命中 | **只读视图 + 预填跳转**，不跨域写、不自动算金额 |
| 11 | 验证数据 | 幂等演示种子脚本（`-Force` 造 / `-Clean` 清） |

## 2. 数据库

### 2.1 新表 `nc_biz_death_declarations`（申报台账）

权威定义：`Resources/Schema/death_declarations/database.yaml`（SchemaService 幂等建表/索引/外键）；
部署副本：`docs/migrations/20261026_death_declarations_and_death_time.sql`（幂等，含同结构 DDL）。

| 分组 | 列 |
|---|---|
| 死者 | `deceased_name` `deceased_id_card` `deceased_relation` |
| 死亡确切时间 | `death_date date NOT NULL`、**`death_time time NOT NULL`**、`death_reason`、`death_certificate_no`、`death_place` |
| 申报 | `declared_by_name` `declared_by_id_card` `declared_by_phone` `declared_by_type`、`declared_at DEFAULT NOW()`、`declare_channel`、`status` |
| 关联（可空） | `application_id`（无档案村民为 NULL）、`death_record_id`（一期不回填） |
| 归属系统 | `village_id` `town_id` `village_name` `operator_name` `remark` `created_by/created_at/updated_at/deleted_at` |

- **无唯一约束**：允许多次申报；重复由提交前校验（±3 天窗口）+ 提醒规则检测；作废走 `status='Revoked'`（软状态，不物理删）。
- 索引：`idx_biz_decl_id_card` `idx_biz_decl_death_date` `idx_biz_decl_village` `idx_biz_decl_declared_at`。
- 状态与申报人类型常量：`Constants/DeathDeclarationConstants.cs`（Pending/Verified/Revoked；家属/村民委员会/医疗机构/公安机关/其他）。

### 2.1.1 核实说明要素 7 列（2026-10-26 迁移 `20261026_death_declaration_verify_details.sql`）

《死亡情况核实说明》模板正文需要**报告人、现场所见、遗体安置、业务两项**，必须落库（否则三联出件后无法补打、无法审计）：

| 列 | 类型 | 模板占位符 |
|---|---|---|
| `reporter_name` | varchar(100) | `{死者报告人}`（发现/报告人，**与申报人 `declared_by_*` 独立手填**） |
| `reporter_relation` | varchar(50) | `{死者报告人与死者关系}` |
| `reporter_phone` | varchar(20) | `{死者报告人联系方式}` |
| `situation_desc` | text | `{死者情况描述}`（现场所见情况，长文本） |
| `remains_arrangement` | text | `{死亡人遗体安置情况}` |
| `business_agent` | varchar(100) | `{业务办理人}` |
| `business_matter` | varchar(200) | `{相关业务事项}`（默认「申请居民死亡医学证明」） |

> 全部可空：历史行与「只出文书」场景兼容；新申报由表单必填策略控制（报告人姓名必填、镇级账号「所在村」必填）。
> 所在村：镇级降级申报写入既有 `village_name` 列（村级申报自动取组织村）。

### 2.2 既有 `nc_biz_death_records` 补列

| 列 | 类型 | 说明 |
|---|---|---|
| `death_time` | `time NULL` | **新写入必填**（应用层双门）；存量行无法回填真实时刻故 DB 允许 NULL，为空时进提醒 #11 并在文书显示「（时刻未记录）」 |

时间拼装**单点**：`DeathStatementService.FormatDeathDateTime(date, time)` → `2026年10月26日 14:30`。

### 2.3 组织机构省级级联（2026-10-26，为落款 `{所在省}`）

原区划只有 市→县→镇→村 四级，组织机构没有省 → 落款五段出不全。本轮建**真级联省表**（非文本字段）：

## 3. 服务与查询口径

`Services/Domain/ArchiveManagement/IDeathStatementService.cs` / `DeathStatementService.cs`

### 3.1 本村范围（唯一口径：`Helpers/VillageScopeResolver.cs`）

- `ResolveScopeAsync`：`App.CurrentUserOrganizationId` → `IOrganizationService.GetByIdAsync` → `VillageId/VillageName`；
  **取不到 → `Result.Failure`「当前账号未绑定村/社区」**，页面禁用查询，禁止静默放开全库。
- 匹配规则：数值ID 精确匹配 **OR** 文本村名后缀归一化相等（`regexp_replace(...,'(村民委员会|居民委员会|村公所|居委会|村委会|委员会|社区|村)+$','')`）。
- 归一化实现：`VillageScopeResolver.StripSuffix/Normalize/NameMatchSql`，与 `PublicityVillageResolver` 同口径，**各查询禁止另写一套村过滤**。
- 无村字段的记录视为不可判定 → 计入本村（临救 `village` 为空、追缴表无村字段等）。

### 3.2 搜索（`SearchAsync`）

- 主源：申报台账 `DISTINCT ON (deceased_id_card) ... ORDER BY deceased_id_card, declared_at DESC LIMIT 50`（每死者取最新一条；
  `showAll=true` 才含作废）。
- 补充候选：本村 `nc_biz_death_records` 中**无有效申报**者 → `Badge=未申报`。
- 日期范围按 `death_date` 范围比较（`>= from AND < to+1d`），**禁止 `EXTRACT`**。

### 3.3 身份七源（`GetIdentitiesAsync`，单身份证批查 + 每源 LIMIT）

> ⚠️ **表名一律以 `Resources/Schema/{域}/database.yaml` 为准，实现时禁止凭印象写表名。**
> 2026-10-26 实例：临时救助表写成 `nc_biz_temp_relief`（真实表名 `nc_biz_temp_relief_applications`）→ 42P01，
> 且因失败消息未带源名，定位被拖慢；现 7 源失败消息统一带「（×××源）」前缀。

| # | 源 | 表 | 本村判定 |
|---|---|---|---|
| 1 | 低收入人口（12 分类） | `nc_biz_applications`（`applicant_id_card` 或 `nc_biz_family_members.id_card` 命中） | `village_id`/`hukou_village_id`/`community` |
| 2 | 普惠高龄 | `nc_biz_elderly_applications` | `family_village_id`/`hukou_village_id` |
| 3 | 残疾人 | `nc_biz_family_members.is_disabled` + 档案 | 同 1 |
| 4 | 大学生 | `nc_biz_college_students` + 档案 | 同 1 |
| 5 | 临时救助 | `nc_biz_temp_relief_applications`（`applicant_id_card`/`beneficiary_id_card`） | `village` 文本归一化 |
| 6 | 近亲属备案 | `nc_biz_near_relative_links` + 档案 | 档案为空则计入本村 |
| 7 | 后补追缴 | `nc_biz_recovery_records`（⚠ 尚未登记进 Schema yaml，靠 `docs/migrations/20261019_recovery_amount_source.sql` 建表） | 表无村字段 → 按身份证计入本村 |

**跨村命中**：`CrossVillageCount++`，不进 `Identities`，只进提醒 #5（只给计数，不带他村 PII）。

| `DEATH_RELATION` / `DECLARED_RELATION` | 与户主关系 / 与申报人关系 |
| `DEATH_VILLAGE` / `DEATH_TOWN` / `DEATH_ADDRESS` | 村社区 / 乡镇 / 家庭住址 |

| `DECLARED_BY_NAME` / `DECLARED_BY_ID_CARD` / `DECLARED_BY_PHONE` / `DECLARED_BY_TYPE` / `DECLARED_AT` | 申报人五要素 |
| `DEATH_ISSUE_UNIT` / `DEATH_ISSUE_DATE` | 出具单位 / 出具日期（落款） |
| `OPERATOR_NAME` / `OPERATOR_UNIT` / `OPERATOR_UNIT_PHONE` | 经办人 / 单位 / 电话（复用既有键） |
| `DEATH_IDENTITY_COUNT` / `DEATH_REMIND_COUNT` | 身份条数 / 提醒条数 |
| `DEATH_IDENTITY_{TYPE,STATUS,PERIOD,SOURCE,NOTE}_1..12` | 身份清单表 12 行 × 5 列（超出部分由 `DEATH_IDENTITY_COUNT` 提示） |
| `DEATH_REMIND_{LEVEL,TEXT}_1..8` | 数据提醒 8 行 × 2 列 |
| `PROVINCE` / `CITY` / `DISTRICT` / `DEATH_TOWN` / `DEATH_VILLAGE` | **落款五段** `{所在省}{所在市}{所在县区}{所在乡镇}{所在村}村民委员会`（省/市/县区取自组织机构；镇级降级时村取表单手填的「所在村」） |
| `DEATH_GENDER` / `DEATH_ETHNICITY` | 死者性别（档案 Gender，为空按身份证 `IdCardValidator.ExtractGender` 推导）/ 民族（档案 Ethnicity → `IDictCacheService(Ethnicities)` 转显示名） |
| `PUSH_UNIT` | **推送单位**（三联各异：村留存 / 镇政府 / 镇中心卫生院，见 §6.4） |
| `DEATH_REPORTER_NAME` / `DEATH_REPORTER_RELATION` / `DEATH_REPORTER_PHONE` | 发现（报告）人三要素（与申报人独立手填） |
| `DEATH_SITUATION_DESC` / `DEATH_REMAINS_ARRANGEMENT` | 现场所见情况 / 遗体安置情况（长文本） |
| `BUSINESS_AGENT` / `BUSINESS_MATTER` | 业务办理人 / 相关业务事项（默认「申请居民死亡医学证明」） |

> 槽位全部**显式供给**（空位给空串），杜绝占位符残留；超出容量时条数键提示实际数量。
> `{印章}` **不是字段**：模板里写成纯文本 `(印章)`，config 不声明 → 引擎不替换，出件后纸质盖章。

- 落款：`{所在省}{所在市}{所在县区}{所在乡镇}{所在村}村民委员会` + `{填写日期}` + `(印章)` + 手写签名位
- 「经办人签字：/ 联系方式：」无占位符，纸质手填

### 6.4 三联出具（2026-10-26）

业务要求：一次申报要出**三份** —— 一份村里留存、一份交镇政府相关部门、一份给镇中心卫生院（**用于申报申请死亡证明**）。
三份的 `{推送单位}` **不同** → **不能用份数复制（copies=3）**，必须逐份生成：

| 联次 | 默认推送单位 | 复选 |
|---|---|---|
| 村留存 | `{所在村}村民委员会（本委存档）` | `PrintRetain` |
| 交镇政府 | `{所在乡镇}人民政府` | `PrintGov` |
| 给卫生院 | `{所在乡镇}中心卫生院` | `PrintClinic` |

- 实现：Tab③「三联出具」区（3 个可编辑 `Entry` + 3 个复选，默认全选）→ `PrintTripleCommand`
  = `PrintTripleAsync()`：循环 `ExecutePrintAsync` 逐份出件，**每份独立批次号**（留痕可按模板名归组），
  落盘文件由 `OutputPathHelper` 时间戳区分（同目录三个文件）；手机端为 `PushPrintTripleCommand`（逐份入队 PC 打印代理）
- 默认值按组织镇/村名推导，改一次用 `Preferences` 记住（同镇后续文书不必重填）
- 预览默认展示「镇政府」联（`CurrentPushUnit()`）
- 权限：每份都走 `PRINT_LOWINCOMEPROOF`（`PrintExecuteService.PrintPermissionMap["DeathStatement"]`）

## 8. 冒烟清单

1. Schema 校验：新表与 `death_records.death_time` 全绿；`dotnet build` 0 错 0 警；`Scripts\check_template_fields.ps1` 通过。
2. 未绑定村社区账号进入 → 页头红条显式报错、无法搜索（不静默放开全库）。
3. `-Force` 造数后搜索 → 3 名演示死者（含「未申报」候选；勾「含作废申报」多一条）。
4. 选中重复申报者 → 提醒出现「疑似重复申报」「缺死亡证明编号」；跨村场景见提醒 #5（计数）。
4a. **Tab② 身份与提醒：七源聚合无 `42P01`；任一源失败时错误消息带「（×××源）」标识**（快速定位是哪张表）。
4b. Tab③ 三联出具：村留存/镇政府/卫生院各出一份，`推送单位` 三份不同、留痕 3 条同 `batchNo`、落盘 3 个文件。
5. 手工录入（无档案村民）→ 「汇总身份」显示无记录提醒 → 提交申报 → 台账 `declared_at` 为提交时刻、`death_time` 为所填时刻。
6. 3 天窗口内再次提交 → 弹「重复申报确认」。
7. 作废 → 状态变「已作废」、默认列表不再出现；核实 → 状态「已核实」。
8. 户主死亡变更（PC + 手机）不填时刻被拦 / 成员变更选「人员死亡」才出现时刻选择器，填了落库 `death_time` 正确。
9. 联动卡片：高龄在享 → 跳停发页（原因预选去世、日期回填）；户主 → 跳户主死亡变更（日期/时刻/原因/编号回填）；办完回页卡片转绿。
10. 首页第四条横幅计数与页面未办联动一致；查询失败不亮横幅。
11. 模板已上传 → 预览无占位符残留 → 打印/保存留痕 `nc_biz_print_records`（business_type=`DeathStatement`）+ 落盘 `{输出根}/死亡情况说明/…`；未上传 → 友好提示不崩溃。
12. 无 `PRINT_LOWINCOMEPROOF` 权限 → 打印/保存/推送按钮禁用或报「缺权限」。
13. `-Clean` 后演示行清空。

## 9. 边界与未含

1. **5 个历史导入库**不在一期（只有文本村字段且无统一 ID）。
2. **高龄停发表自身 `death_date`**（`nc_biz_elderly_applications`）不改，只做预填跳转。
3. `ChangeService.DeathAndQueries.ProcessMemberDeathAsync` 全仓无调用方（疑似死代码）：已同步加 `DeathTime` 与必填校验，但未追调用链。
4. 不新增「办结回写表」：联动已办状态由目标域自身状态实时判定。
5. 不自动计算任何金额（追缴、保障金一律人工核定，AGENTS §9-7）。
