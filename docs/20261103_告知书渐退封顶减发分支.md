## 1. 业务口径

模板**全库唯一**（`nc_biz_templates` 241），「停保 / 不予认定 / 终止 / 待遇调整」是同一模板的不同**方向**，
方向由 `ArchiveProductionViewModel` 装配端按事实分支填 `NOTICE_*`。本次为方向③补第二个子场景：

| 顺序 | 方向/子场景 | 事实来源 | 说明 |
|---|---|---|---|
| ① | 户主死亡整户停止 | `GetLatestHouseholdDeathStopRecordAsync` | 不受单人保排除 |
| ② | 停保 / 不予认定 | `GetLatestTriggeredStopRecordAsync`；兜底：归档终结拒保（`Stopped` + 自身停保码、无变更记录） | 受单人保排除 |
| ③a | 待遇调整·**登记**（**优先**） | `GetLatestFundChangeRegistrationAsync`（`change_reason_type='保障金变更登记'`） | 受单人保排除 |
| ③b | 待遇调整·**渐退封顶减发**（本次新增） | `GracePeriodService.GetActiveAsync`：`原额 > 封顶现发 > 0` | 受单人保排除 |
| ④ | 落空 | 上述皆空且 `status=Stopped` → `Warn`「若输出告知书将为空白」 | 可观测护栏 |

**互斥**：渐退活跃时服务端**跳过**保障金变更登记（`ChangeService.RebuildAndReview.cs` 渐退期互斥注释），
故 ③a/③b 业务互斥；装配端仍按 **登记优先** 的 `if/else` 顺序判定，历史并存数据也只走 ③a。

**单人保排除（2026-11 拍板）**：单人保虽可触发封顶减发（上限 = 标准 × 1 人），业务口径**同样排除**——
与 ②③a 归入同一 `!IsCodeSingleRescue` 条件，清单门与装配端两处一致。

## 2. 金额与文案口径

- **金额权威**：`ApplicationFormViewModel.ApplyGraceCapAsync`
  - 原额 `OriginalGuaranteeAmount`（链上优先取上游档案）
  - 上限 = 户口类型最低保障标准 × 新家庭人数（**不含分类施保**）
  - 现发 `GraceGrantAmount = min(原额, 上限)`；减发 = 原额 − 现发
  - 落库 `nc_biz_grace_periods.original_guarantee_amount / grace_grant_amount`；口径 = **户月保障金**
- **取数同源**：清单门 `ChangeDocumentFacts.HasGrantReduce` 与装配端
  `TryFillGraceCapReduceNoticeAsync` 都走 `_gracePeriodService.GetActiveAsync`（`is_active=TRUE`），
  `is_active` 只在表单保存判定退出渐退时被 `ClearAsync` 置 false（期满不清）→ **两侧永不劈叉**
- **A2 文案**（`NOTICE_DETAILED_REASON`）：

  ```
  经审核，你户月保障金由{原额:F2}元调整为{现发:F2}元（减发{差额:F2}元/月），已进入渐退期（{N}个月，至{止期:yyyy年M月d日}），期内按封顶标准发放
  ```

  降级：`EndDate` 缺失 → 去掉「，至…」；`Months` 缺失 → 只留「，至…」；两者皆空 → 去掉整个括号段（**不出空括号**）
- 其余字段与方向③a 逐字同源：`NOTICE_BUSINESS_CATEGORY=变更`、`NOTICE_BENEFIT_TYPE=调整享受`、
  `NOTICE_BENEFIT_RESULT=社会救助保障待遇`、`NOTICE_HANDLING_CATEGORY=渐退登记原分类（回落档案自身分类）`、
  `COMMUNITY/FAMILY_SIZE_TEXT/CUSTOM_REASON/DELIVERER/ORG_UNIT/DATE` 同取值
