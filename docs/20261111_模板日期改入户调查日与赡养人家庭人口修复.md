| fieldKey | `PUBLICITY_RANGE`（"起 至 止"合成串） | `PUBLICITY_START_DATE`（ISO 原值） |

- `ApplyFormat` 见 format 以 `y` 开头 → `DateTime.TryParse(ISO)` → `2026年11月`。

## 4. 赡养抚养扶养「家庭人口」字段缺失（低收入人口认定申请）

### 4.1 根因一：UI 看不见

`Components\FamilyMemberCardView.xaml` 分区5 的 Grid **只有 8 列**（`Auto,*,Auto,*,Auto,*,Auto,*`，索引 0-7），
但「家庭人口」Label/Entry 写 `Grid.Column="8"/"9"` → MAUI `GridLayoutManager` 对越界列做
`Clamp(0, 列数-1)` → 两者与第 7 列的「月收入」输入框**同格重叠**，后绘制的 Entry 盖住 Label
→ 视觉上完全看不到该字段。

**回归来源**：commit `3e6128a`（2026-11-03 表单模板收敛）。收敛前赡养卡是 10 列、共同生活卡是 8 列，
合并为共享组件时统一用了 8 列。移动版是内联模板（`MobileApplicationFormStep2View.xaml:442-451`，
`*,*` 两列），**不受影响**。

**修法**：移出原 Grid，另起一个 `ColumnDefinitions="Auto,*"` 的独立 Grid，
整块 `IsVisible="{Binding ShowFamilySize…}"` —— 共同生活卡（`ShowFamilySize=False`）整块隐藏零影响，
赡养卡显示且输入框宽度占满剩余空间。

### 4.2 根因二：数据被覆盖（修 UI 后立刻暴露）

Step2 的 `FamilyMember.FamilySize` 与 Step3 的 `Supporter.SupporterFamilySize` 落在
**同一列** `nc_biz_family_members.family_size`（`Supporter.Id == FamilyMember.Id`，同一行）。
保存顺序 `SaveFamilyMembersAsync` 先写、`SaveSupportersAsync` 后写 → **后者覆盖前者**：

- `BuildSupporterFromMember`（`DetailCommands.cs:478`）原硬编码 `SupporterFamilySize = 1`，不带 `member.FamilySize`；
- `SyncSupporterBasicsFromMember` 刻意不同步（"保留 Step3 编辑的家庭人数"）。

→ Step2 填的值保存后被改回 1/旧值；连带 **模板74（低收入审核确认表）赡养义务人家庭人口/合计**
（`ArchiveProductionViewModel.cs:1414 / 1438` 读 `FamilyMember.FamilySize`）恒取 1、合计失真。

**语义确认（用户 2026-11-11）**：家庭人口 = **赡养人自己家庭的人口，与当前认定的家庭无关**。
两处是同一个值的两个编辑口 → 必须保持一致。

**修法**（单点 `Helpers\SupporterFamilySizeReconciler.cs`，纯逻辑可单测）：

1. `BuildSupporterFromMember` → `SupporterFamilySize = member.FamilySize ?? 1`（新增时即同值）。
2. 新增 `ReconcileSupporterFamilySizes()`，调用点 **两处保存路径**、均在
   `MergeSupportMembersIntoSupportersAsync()` 之后、`SaveFamilyMembersAsync` **之前**：
   - `ApplicationFormViewModel.ClassificationAndSave.cs` `SaveApplicationInternalAsync`
   - `ApplicationFormViewModel.ValidationAndSubmit.cs` 成员变更/停旧建新事务
3. 加载基线 `_loadedFamilySizeByIdCard`（身份证 → family_size 值拷贝），建于
   `Initialization.cs` `_loadedMemberCategoryByIdCard` 旁，同写法。
   **必须有基线**：只比两侧现值无法分辨"Step2 改过"还是"Step3 改过"——两者都表现为"两边不等"。

判定规则（详见类注释 + 单测）：

| 情形 | 结果 |
|---|---|
| 两侧同值 | 不动（覆盖本会话新增，已由 4.2-1 同值播种） |
| Step2 侧为 null | 以 Step3 为准（含"基线 NULL vs 加载兜底 1"归一化差异） |
| Step2 偏离基线（**含两侧都改的冲突**、无基线=新增） | **Step2 为准** |
| 仅 Step3 偏离基线 | Step3 为准 |
| Step3 手动 `+赡养` 无对应成员行 | 不参与调和，原样保存 |

4. `FamilyMember.FamilySize` 由普通自动属性改为**发变更通知**的属性，否则调和后 Step2 卡不刷新。

## 6. 重构说明

`ResolveSurveyDate` 原有两份同构拷贝（`ArchiveProductionViewModel` 输出 `yyyy年M月d日`、
`TemplateFieldBuilder` 输出 `yyyy年MM月dd日`，2026-10-16 手工同步）。本次资产核查链路需要第三处，

**各自 format 串保持不变**，避免第三份拷贝漂移。
