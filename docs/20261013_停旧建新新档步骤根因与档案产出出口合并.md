## §2 根因一：新档数据齐全却停在 step=1

### 2.1 步骤与 Tab 的口径（唯一事实来源 `Constants/WorkflowSteps.cs`）

| step | 语义 | 所在 Tab | 查询条件 |
|---|---|---|---|
| 1~4 | 录入阶段 | 草稿 | `status=Draft AND current_step < 5`（`ApplicationService.cs:1173`） |
| 5 | 五个录入步骤全部完成，待归档 | 已建档未提交 | `status=Draft AND current_step = 5`（`:967`） |
| 6 | 已归档完结 | 已完结档案 | `current_step=6 AND status IN (Approved,Completed,Stopped)`（`:1019`） |

归档门槛在 `ApplicationStatusService.cs:57`：

```csharp
if (current.CurrentStep < WorkflowSteps.PENDING_ARCHIVE)
    return Result.Failure(..., $"档案录入未完成（当前第 {current.CurrentStep} 步，需完成第 5 步），不能完成归档");
```

### 2.2 问题所在

`ChangeService.StopAndRebuildAsync`（`RebuildAndReview.cs`）是「停旧建新」的唯一实现，三条业务路径共用：

- 成员变更（`RebuildAndReview.cs`，`MEMBER_CHANGE`）
- 经济复核（`RebuildAndReview.cs`，`CATEGORY_REBUILD`）
- 户主死亡（`ChangeService.DeathAndQueries.cs`）

它把旧档**完整复制**到新档——主表、家庭成员、经济明细（劳动收入/土地/补贴/大学生/入户调查）、照料人，并经 `applyOverrides` 覆盖本次重判后的 `classification_result`/`is_eligible`/保障金。**五个录入步骤的数据其实全齐了**，却把 `current_step` 写成 `ENTRY_START(1)`。

于是在「保存完成员变更 → 档案产出页」这条主路径上，新档必然够不着归档门槛：

| 用户选的出口 | 实际结果 |
|---|---|
| 整套档案 | 「完成归档」按钮在，**点了必失败**（step=1 < 5） |
| 仅出文书 | 按钮被 `IsDocumentMode` 隐藏，静默无事发生 |
| 稍后再说 | 新档留在草稿 step=1 |

唯一能推进的路是：退回工作流 →「草稿」Tab 编辑打开 → 把**复制来的**五步重走一遍 → 保存到 step5 → 再归档。app90（21:41 那次保存）与 app80（户主死亡路径）都停在 `Draft/5`，说明三条链路都踩同一个坑。

### 2.3 修复

`RebuildAndReview.cs` 的新档 INSERT 参数 `WorkflowSteps.ENTRY_START` → `WorkflowSteps.PENDING_ARCHIVE`，并补齐方法注释与第 3 步的说明。

**效果**：新档直接进「已建档未提交」Tab，档案产出页的「完成归档」立即可用；从该 Tab 编辑打开时表单落在第 5 步，仍可「上一步」改任意内容。

**已排除的风险**：`Draft+step5` 只是列表分区，全库无任何批量/自动任务消费该状态（三个查询均为纯分页）。

## §3 根因二：「预勾选模板」与「禁止归档」共用一个开关

`ArchiveOutputViewModel.cs:323-327`：

```csharp
IsTemplateFilterMode = templateFilter is { Length: > 0 };
IsDocumentMode = !IsTemplateFilterMode
    && (outCats is { Length: > 0 } || operationOverride != null || preselect is { Length: > 0 });
```

而 `IsCompleteArchiveVisible = !IsTemplateFilterMode && !IsDocumentMode`，且 `CompleteAsync` 在入口直接 return（`BatchAndArchive.cs:527`）。

「仅出文书」虽然把 `TemplateFilter` 设为 `null`（`ApplyDocumentOutputContext` 里还特意注释"分类+预勾选，非强白名单"），但它设了 `OutputCategories`+`OperationOverride`+`PrefilterTemplateNames` → `IsDocumentMode=true` → **归档能力被一起禁掉**。

**这个绑定本是有意的护栏**——`BatchAndArchive.cs:526` 注释写明"会把渐退草稿 Draft 强行置 Approved/step6"。渐退户确实不该被一键归档。

**但停旧建新的新档必须归档**：旧档已 Stopped，新档不归档，这户就没有任何在保档案（李增会当时正是这个状态）。成员变更与户主变更复用了渐退的「仅出文书」上下文，把"禁归档"也一并继承了——**属误伤**。

## §4 根因三（更实质）：经济复核停旧建新后传的是旧档ID

`ApplicationFormViewModel.ValidationAndSubmit.cs` 经济复核分支：

- `:838` 先拦掉 `!result.Value.Rebuilt`（未生成新档）的情况 → **走到后面时新档必然已建**
- 但 `:859`（渐退分支）与 `:872`（非渐退分支）仍传 `_applicationId`

`_applicationId` 只在加载时（`Initialization.cs:458`）与新建路径（`ClassificationAndSave.cs:983/1045`）赋值，**经济复核路径从未更新过**，所以它始终是被复核的旧档（已 Stopped）。

后果：档案产出页打开的是旧档，文书取旧档数据，归档也作用于旧档；**新档全程没被处理**。

对照另两条链路都是对的：成员变更传 `changeValue.NewApplicationId`、户主变更传 `changeResult.Value?.NewApplicationId`。

### 修复

两处改为 `result.Value.NewApplicationId`，第二参数（变更前旧档ID，停保告知书判定用）传 `_applicationId`。

## §5 出口合并（用户决策：合并成一个）

原先三个出口的真实差别只有两件事——模板范围（全量 vs 预勾选）与归档能力（有 vs 无），而后者被 §3 的绑定绑死在前者上。

| 原出口 | 去向 |
|---|---|
| 整套档案 | **保留**：整档模式，归档可用 |
| 仅出文书 | 删除（预勾选便利丢失，换来归档能力） |
| 稍后再说 | 删除（用户可直接返回，等价于"不点归档"） |

### 5.1 成员变更（`ValidationAndSubmit.cs`）

删掉 `DisplayActionSheetAsync` 与两个分支，统一走 `ClearDocumentOutputContext()` + 导航到 `ArchiveProductionPage`（新档ID + 旧档ID + "成员变更"）。

三字段皆空 → `IsDocumentMode=false` → 归档按钮天然可见，**无需新增任何开关**。

### 5.2 户主变更（`HeadChangeViewModel.cs`）

同样删掉 ActionSheet 与两个分支，保留原「整套档案」分支的四个 `PrintNavigationData` 清空语义。

`NewApplicationId` 兜底逻辑保留（未停旧建新时新档ID 用当前档）；但 `OriginalApplicationId` 取**「仅出文书」分支的语义**——仅在确实产生了新档时才传旧档ID，否则传 `null`。理由：未重建时新旧档同为当前档，把当前档自己当"变更前旧档案"传入会让停保告知书判定拿到自指的原始档。

### 5.3 合并后的行为与退路

- 用户改完成员/户主变更后直接进入档案产出页，不再有选择题
- 想不打文书：直接返回即可（导航栈可 Pop），不点「完成归档」就不会归档
- `CompleteAsync` 自带双重护栏：必须至少生成一个输出文件 + 二次确认（`BatchAndArchive.cs:533/539`）

### 5.4 代价（明确记下）

丢失了「预勾选成员变更表 + 变更告知书」的便利，用户需在产出页自行勾选这两张。

若日后觉得不便，可改为「预勾选 + `AllowCompleteArchive` 显式开关」把禁归档从模板范围上解耦——但那要动 `IsDocumentMode` 判据、波及渐退等所有路径，本轮为控制风险未采用。

## §6 经济复核渐退分支：**刻意保留禁归档**

`ValidationAndSubmit.cs:846-866` 的渐退分支（`IsInGracePeriod` 或超限减发）仍然走 `ApplyDocumentOutputContext`，因此仍处于 `IsDocumentMode`、仍无归档按钮。

**这不是漏改**：渐退户档案仍是 Draft，提前归档置 Approved 会破坏渐退期管理，是刻意的业务规则。

修完 §4 之后，该分支的档案ID 已指向新档，新档以 step5 出现在「已建档未提交」，用户可随时回来归档——比原来"旧档ID + 禁归档 + 新档卡草稿"完整得多。

## §7 顺带排查：family_size 与成员数不一致 —— **不是问题**

排查中发现两户的 `family_size` 与 `nc_biz_family_members` 行数不一致，初判疑为 bug，查证后**排除**：

| 户 | 成员 | `member_category` | 计入家庭人口 |
|---|---|---|---|
| app90 | 李增会 / 张宇昌 / **张微** | Head / SharedLiving / **Support** | 2 ✓ |
| app94 | 梁玉祥 / 梁茗辉 / 刘金梅 / **梁佳宁** | Head / SharedLiving / SharedLiving / **Support** | 3 ✓ |

张微、梁佳宁是**赡养抚养扶养义务人（Support）**，按规则本就不计入家庭人口。与 `ApplicationFormViewModel.DetailCommands.cs` 的 `FamilySize = SharedLivingMembers.Count + 1`（+1 户主）以及 `ChangeViewModel.cs` 的"剔除赡养抚养扶养义务人"口径完全吻合。

**遗留疑点（未修，另开一轮）**：资产核对分支（`ArchiveProductionViewModel.cs` 的 `FamilyInfo`/`APPLICANT_COUNT`/`HEAD_FAMILY_SIZE` 三处）用的是全量 `detail.FamilyMembers.Count`，而社会救助分支一律用 `app.FamilySize`。属另一条路径，是否有意为之待确认。
