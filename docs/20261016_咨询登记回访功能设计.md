## 二、业务确认点（实现前必须逐条拍板）

1. **语义**：咨询登记 = 群众来信来访/电话咨询的登记？与救助申请、资产核验是什么关系（挂靠 or 独立）？
2. **入口**：归资产核验域（T3 所在分类）还是独立菜单？（影响 Page 落点与权限树）
3. **台账形态**：一户一条（单卡）还是一户多条（真台账逐条打印）？当前 T3 是**单值 12 字段**（非槽位）→ 天然单条；多条需改模板加槽位（**不建议首期做**）。
4. **快照 vs 关联**：户主 5 信息（姓名/证号/电话/住址/人口）打印时取**登记当时快照**（台账本义）还是**实时关联档案**（现状即实时）？——快照更符合台账，实时则零改动。
5. **字段增减**：是否需要「咨询内容」「备注」「回访方式（现场/电话）」等 T3 模板没有的字段（模板也要改则另开工单）。
6. **VISIT_STATUS 枚举**：建议 `{已回访, 电话回访, 未联系上, 无需回访}`——请业务定稿。

## 三、方案总览（确认点拍板后按此实施）

### M1 · 数据模型（草案，落 `Resources\Schema\AssetVerification\consult_records.yaml`）

```yaml
table: nc_biz_consult_records
comment: 咨询登记与回访（T3 档案_咨询登记台账 数据源）
columns:
  - { name: id,             type: bigserial,   pk: true }
  - { name: application_id, type: bigint,      null: true, ref: nc_biz_applications(id) }   # 可空：无申请的散客咨询（确认点1/4）
  - { name: applicant_name,  type: varchar(50)  }   # 咨询人（户主）快照 → APPLICANT_NAME
  - { name: applicant_id_card, type: varchar(18) }  # → APPLICANT_ID_CARD
  - { name: contact_phone,   type: varchar(20)  }   # → CONTACT_PHONE
  - { name: family_address,  type: varchar(200) }   # → FAMILY_ADDRESS
  - { name: family_size,     type: int          }   # → HEAD_FAMILY_SIZE
  - { name: consult_at,      type: timestamp    }   # 登记时间 → REPORT_DATE{填报时间}
  - { name: consult_content, type: text, null: true }  # 咨询内容（确认点5：模板暂无此列，仅存档）
  - { name: operator_name,   type: varchar(50)  }   # 登记经办 → OPERATOR_NAME
  - { name: report_unit,     type: varchar(100) }   # 登记单位 → OPERATOR_UNIT
  - { name: visit_at,        type: timestamp, null: true }  # → VISIT_DATE{回访时间}
  - { name: visit_by,        type: varchar(50), null: true } # → VISIT_OPERATOR{回访经办人员}
  - { name: visit_result,    type: varchar(20), null: true } # → VISIT_STATUS{回访情况}（枚举见确认点6）
  - { name: visit_remark,    type: text, null: true }
  - { name: created_by, created_at, updated_at, deleted_at }  # 常规四件套
indexes: [ (application_id), (consult_at desc), (deleted_at) ]
```

- `CIVIL_ASSISTANT_NAME{民政助理姓名}` 不入库：**继续走现流**（登录组织上下文，与打印时点一致——民政助理是"当前经办单位的人"，快照反而错）。
- SchemaService 幂等建表（AGENTS §2），手写迁移仅当需要特殊索引。

### M3 · 打印供给（最小侵入方案）

- **9 登记键不动**（现流已供给、快照/实时之争见确认点4——默认实时=零改动）。
- **只补 3 回访键**：打印/预览 T3 前调 `GetLatestByApplicationIdAsync` →
  `fields[FieldKeys.VISIT_DATE] = visit_at?.ToString("yyyy年M月d日") ?? ""`（同 `VISIT_OPERATOR/VISIT_STATUS`）；
  无记录 → **保持空串**（与今日打印完全一致，零回归）。
- 接入点（实现时二选一，均在选中 T3 模板分支内）：`AssetVerificationReprintProvider`（补打流）与/或 `QuickAssetVerificationViewModel` 打印出口——**以 T3 实际打印入口为准**（实现前先断点确认）。
- ⚠️ 纪律：三键已转正（白名单内），**新增供给即"常量+供给"闭环**（FieldKeys 头注释三同步纪律 §②）。

## 五、风险与边界

1. **域边界**：T3 挂 AssetVerification 分类，但语义近"来访信访"——若业务定独立域，表与 Page 迁出（改 yaml schema 名与目录，成本小，**先拍确认点 1/2**）。
2. **模板单条限制**：真台账（一户多条逐行）需 T3 改槽位模板——首期不做，列为后续（改模板走模板编辑上传，配 `CompositeBeforeSub` 等体检项兜底）。
3. **零回归红线**：M3 未接入前打印 = 今日行为（空三格）；接入后无记录仍空——任何路径不得让占位符原文残留（D1c 已论证"删行更差"）。
4. **发版顺序**：纯新增（表+供给），无 config 迁移 → 随下个版本正常发版（§2），无双写窗口问题。
