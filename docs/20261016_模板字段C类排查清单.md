## 一、结论

`nc_biz_templates.config_json` 的 63 组"同占位符可合并"候选规则中，经**供给点逐条 RHS 比对**后，
**19 组规则 / 70 行**判定为**值源实质不同**，**一律拒绝合并、保持现状**。本清单逐条给"保留 / 错配待修"判定与后续核对动作。

三条铁律先摆明：

1. **合并的唯一合法前提** = 数据源完全同源（同一表达式、同一格式、同一锚点）。C 类全部不满足。
2. **占位符文本相同 ≠ 值相同**。模板作者写 `{填报单位}` 只是版式约定，不同 Builder 往同一个 placeholder 塞的值来自不同实体字段。
3. **体检通过 ≠ 可合并**。C 类键本身都是合法 ASCII 键（在 `FieldKeys` 白名单内），`check_template_fields.ps1`
   的 `Unknown/NonAscii/MultiSource` 三类检查不会命中它们——本清单是体检之外的人工判定层。

## 五、与体检脚本的关系

- `check_template_fields.ps1` **不因 C 类退出**：C 类的键都在白名单、ASCII、同模板内无占位符多值源。
- 发版前体检（批6 已接入 `publish_all.ps1`）实际参数 = `-FailOn NonAscii,MultiSource -MaxUnknown <基线>`：
  **未知孤儿走 `-MaxUnknown` 基线锁而非 `-FailOn Unknown`**——存量孤儿（当前 71 行）直接零容忍会恒失败，
  基线锁只防新增；C 类同理不进自动化。**不要**把 C 类规则做成自动化检查——
  它们的判定依赖人工读码（值源、格式、锚点），机械比对无法替代。
- 若后续有人重提合并，先读本文档第二节证据，再读 `AGENTS.md §9`（金额）、`§14`（权威来源表）。
